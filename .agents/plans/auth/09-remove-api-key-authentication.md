# Remove API-key authentication

This ExecPlan is a living document maintained according to `.agents/PLANS.md`.

## Purpose / Big Picture

Complete the development cutover so every browser user authenticates through a BFF session and every machine authenticates through OAuth Client Credentials. Raw API keys cease to exist in the application, configuration, documentation, and development clients.

## Surprises & Discoveries

- Removing the API-key bridge deletes the only code path that could ever produce a `platform_admin` `AuthPrincipal` without a pre-existing `OrganizationMembership` row — `BffSessionFlowService`'s login flow requires exactly one active membership to exist before a human can even log in, and nothing maps a Keycloak realm role onto local `membershipRole` directly. Without a replacement, this PR would leave the API in a "can never create the first organization" dead end, contradicting its own "the full API works after a clean development reset" acceptance criterion. Traced the actual `platform:admin`-gated code paths (`POST /v1/organizations`, `/credits/:id`, `/v1/proxies`) and confirmed none of them discriminate on `credentialKind` — `RolePermissionPolicy` returns a `service_client` principal's `permissions` verbatim. Resolved by granting the pre-provisioned dev M2M client (`lef-development-service`) a locally-seeded `platform:admin` `ServiceCredential` instead of provisioning a human platform-admin identity — matching this plan's own "Local bootstrap uses a seeded Keycloak service client" acceptance criterion literally. A real human platform operator identity is `auth/10`'s job ("Seed one platform operator...").
- `ServiceCredential.keycloakClientId` (added in PR 8) had a *globally* unique index, but the bootstrap script needs two rows for the same underlying `lef-development-service` client — one per issuer, since the smtp-dev overlay's containerized `api` must verify tokens against a different (container-internal) Keycloak hostname than the base stack's browser-facing one (see next point). Relaxed the index to `(issuer, keycloakClientId)`, which is the invariant PR 8's own rotate/delete lookups actually needed — no PR 8 behavior depended on global uniqueness.
- `OIDC_ISSUER_URL` does double duty: `JoseOidcTokenVerifier` uses it server-side for JWKS fetch + issuer-claim pinning, while `KeycloakOAuthClient` uses the *same* config value to build the browser-facing authorization/logout redirect URL. The base stack's `http://localhost:58080/...` value is correct for the browser (must stay host-reachable) but is unreachable from inside the `api` container's own network namespace — confirmed empirically (a real OAuth bearer token from the base stack's issuer gets `401 OIDC access token is invalid` against the containerized API, in ~7ms, consistent with an immediate ECONNREFUSED, not a JWKS timeout). This is a pre-existing gap (M2M-over-container was simply never exercised before, since `X-Api-Key` never touched Keycloak) that X-Api-Key's removal makes newly load-bearing for every Bruno collection that used to rely on the admin key. Fixed narrowly: `docker/compose.smtp-dev.yaml` overrides `OIDC_ISSUER_URL` to the container-internal `http://keycloak:8080/...` for its own `api` override only (that overlay never drives a browser login), leaving the base stack's browser-facing config untouched.
- That same base-stack container-networking gap means every Bruno collection now authenticating via a real OAuth Client Credentials token (`proxy-registry`, `organization-onboarding` 02/05, `service-client-management`) must run against a **host-run** API instance, not the container — the same workaround `bruno/organization-onboarding/README.md` already documented for its Keycloak-Admin-API-touching requests, now extended to cover token *verification* too, for a materially larger set of requests than before.
- `@usebruno/cli`'s default (`safe`) sandbox has no `fetch` — the shared collection-root token-minting script needs `--sandbox developer`. Confirmed by reading the sandbox's own allowed-globals list and reproducing the failure (`ReferenceError: 'fetch' is not defined`) before finding the flag.
- `docker/compose.smtp-dev.yaml` bind-mounting `.dev/keycloak/service-client.json` into the `smtp-dev-proxy-bootstrap`/`cleanup` containers failed with `Permission denied`: `provision.ts` wrote that file `0o600` (owner-only), and the `curlimages/curl` image runs as a different, non-root UID. Loosened that one file (not the BFF/org-admin secrets files, which have no new container consumer) to `0o644` — it's a gitignored, dev-only artifact regenerated by `keycloak:provision`, the same risk class as the Docker secrets it replaces.
- The smtp-dev overlay's own Bruno collection cannot be driven from the host at all once its `api` container's issuer is pinned to `keycloak:8080` (unreachable from the host, by design — this is a Docker-internal-only hostname). Resolved by documenting a `docker run --network lef_default node:22-alpine ...` recipe that runs `bru` itself inside a throwaway container attached to the same network, with `baseUrl` overridden to the container-internal `http://api:3000`; verified this recipe end to end (all 6 requests passing, including the SMTP fixture round trip).

## Decision Log

- Decision: Perform an immediate breaking development cutover with no compatibility window.
  Rationale: There is no production environment or customer data to migrate.
  Date/Author: 2026-08-14, project planning.
- Decision: Grant the pre-provisioned `lef-development-service` M2M client a locally-seeded `platform:admin` `ServiceCredential` (via a new `pnpm keycloak:bootstrap-credential` script) as this plan's own local-bootstrap replacement for the deleted admin API key, rather than provisioning a human platform-admin Keycloak identity.
  Rationale: No code path discriminates `platform:admin`-gated routes by `credentialKind`; a service-client credential satisfies every acceptance criterion this plan actually states ("Local bootstrap uses a seeded Keycloak service client") without duplicating `auth/10`'s explicitly-scoped "seed one platform operator" work. A human platform-admin identity also can't self-bootstrap anyway: BFF login requires a pre-existing membership to exist before anyone can log in at all.
  Date/Author: 2026-08-19, implementation.
- Decision: `keycloak:bootstrap-credential` is a separate, manually-run script (`ts-node scripts/keycloak/bootstrap-credential.ts`), not chained into `keycloak:provision` or any composite command.
  Rationale: `auth/10` explicitly owns building the unified, confirmation-gated one-command reset/reseed workflow with a fuller fixture set (customer org, human member, credit balance, M2M client); this plan needs only the minimal piece required to keep the API usable on its own, matching `provisioning.ts`/`provision.ts`'s own existing separation between the realm-provisioning library and its thin CLI entry point.
  Date/Author: 2026-08-19, implementation.
- Decision: `docker/compose.smtp-dev.yaml` overrides `OIDC_ISSUER_URL` to the container-internal Keycloak hostname for its own `api` service only; the base stack's browser-facing value is untouched.
  Rationale: `OIDC_ISSUER_URL` is read for two different audiences (server-side JWKS/issuer verification vs. the browser-facing BFF redirect URL) that need different hostnames; the smtp-dev overlay never drives a browser login, so it's safe to repoint there without affecting `auth/06`'s BFF flow.
  Date/Author: 2026-08-19, implementation.

## Outcomes & Retrospective

All acceptance criteria implemented and verified. `pnpm typecheck`/`pnpm lint` clean. Full jest suite (111 suites / 646 tests, 1 todo, 0 skipped) passed with every live gate active simultaneously across 6 dedicated test databases — zero regressions from the removal sweep.

Live-stack verification, from a from-scratch rebuild through `pnpm keycloak:provision && pnpm keycloak:bootstrap-credential` (idempotent on repeat runs against the same volumes) and `pnpm keycloak:smoke`: confirmed a raw `X-Api-Key`/legacy-token request is rejected everywhere (the scheme no longer exists in `CredentialExtractor` at all), confirmed the seeded `lef-development-service` service credential mints a working `platform:admin` client_credentials token, and confirmed `docker/smtp-dev/bootstrap-proxy.sh`'s OAuth rewrite actually registers the local SMTP proxy (verified directly against the `proxy_registry` table, not just a 200 status). `bru run` (via `npx @usebruno/cli run --env local --sandbox developer`) passed for every affected collection: `proxy-registry` (8/8), `organization-onboarding` (6/6, host-run), `service-client-management` (4/4, host-run), `smtp-dev` (6/6, run inside a throwaway container on the smtp-dev Docker network), `m2m-oidc-authentication` (3/3, container, regression) and `bff-sessions` (5/5, container, regression). `bruno/api-key-administration` was deleted outright.

Final repository sweep (`grep -rln` for `X-Api-Key`, `x-api-key`, `ADMIN_API_KEY`, `admin_apikey`, `api-key-administration`, `Legacy API keys`, `legacy_api_key`, `LEGACY_BRIDGE`, `ApiKeyModule`, `ApiKeyService`, `ApiKeyGuard`, `AdminKeySeeder`, `KeyPermissions`, `modules/api-key`, across the whole repository excluding `.agents/plans/` history and `node_modules/`) returned zero hits, including a stray `docker/smtp-dev`-adjacent `src/lead-email-finder-api/src/email-verification-module/reqs.rest` VS-Code REST Client scratch file that was in scope as live developer tooling.

## Context and Orientation

The preceding plans leave the existing `src/libs/modules/api-key` path available only to keep intermediate branches usable. Credits and jobs no longer depend on tokens, and customer M2M clients can be created through Keycloak, so the bridge can now be deleted.

## Scope and Non-Goals

Remove the API-key module, entity, guards, services, seeding, administration routes, permission checks, token-addressed credits, Docker secrets, and documentation. Update all Bruno collections and development bootstrap scripts to request Keycloak tokens. Do not add deprecation headers, sunset periods, data conversion, or migration code.

## Plan of Work

Delete API-key composition and references after proving each consumer has an OAuth replacement. Remove obsolete environment variables and secret mounts. Add a shared Bruno pre-request or helper flow that requests and caches a short-lived Client Credentials token without committing credentials. Update Swagger and README to describe only OIDC bearer and BFF sessions.

## Interfaces and Dependencies

`X-Api-Key`, `Bearer api_*`, `/v1/api-keys`, and token-addressed credit routes are removed. This plan depends on PR 8 and completes the authentication cutover.

## Acceptance Criteria

- `X-Api-Key` and `Bearer api_*` are rejected on every protected endpoint.
- No API-key generation, listing, revocation, or permission-check route remains.
- No raw-token persistence or token-owned credit contract remains.
- Bruno collections obtain tokens through Client Credentials.
- Local bootstrap uses a seeded Keycloak service client.
- Swagger and README describe only OIDC bearer and BFF-session authentication.
- Obsolete API-key environment variables, secrets, aliases, and tests are removed.
- The full API works after a clean development reset without migration.

## Validation

Search the repository for obsolete module symbols, routes, headers, and secret names. Run full static and test checks, Bruno authentication/endpoint smoke tests, and clean-stack runtime verification.

## Idempotence and Recovery

The cutover deliberately discards development API keys. If the new stack needs to be recreated, use the reset/reseed workflow. Reverting the PR restores source code but not discarded development secrets, which are not preserved by design.
