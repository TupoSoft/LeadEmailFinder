## Scope and Terminology

This contract covers customer-supplied target email addresses and data derived while checking whether those addresses
can plausibly receive mail. It follows that data through HTTP, PostgreSQL, BullMQ and Redis, S3-compatible object
storage, DNS, SMTP, egress proxies, optional HTTP account-discovery providers, application logs, operator surfaces,
managed copies, and customer-directed responses.

The terms below have specific engineering meanings:

- **Customer controller** means the organization that supplies a target address and decides the purpose and lawful
  basis for using the verification service.
- **Processor/service-provider posture** means LeadEmailFinder may process customer-verification data only on the
  supplying organization's documented instructions and for that organization's benefit. It is not, by itself, a
  legal classification or executed contract.
- **Controller data** means account, identity, authentication, organization, billing, fraud-prevention, security,
  incident, audit, and legal-compliance records whose purposes LeadEmailFinder determines separately.
- **Verification inference** includes normalized address parts; format; MX and target-exchange data; mailbox and
  catch-all outcomes; reason and source labels; timestamps; job state; and batch relationships.
- **Managed processor copy** means a customer-verification copy in a log or backup service operated for
  LeadEmailFinder. A mixed store qualifies only when the processor copy has an independently enforceable policy
  boundary.
- **Current lifecycle** describes what the reviewed source does now. **Engineering default** is a normative maximum
  for later enforcement and is not evidence that deletion currently occurs.

## Purpose Limitation

LeadEmailFinder may normalize, route, probe, infer, cache, return, protect, and delete customer-verification data only
as needed to provide the instructed verification service and its approved support, security, and rights workflows.

The following uses are prohibited:

- Reusing an address, cache record, inference, or result across customer organizations;
- Selling, sharing, licensing, or disclosing customer-verification data for LeadEmailFinder's independent benefit;
- Enriching a LeadEmailFinder-owned profile or independently building an audience, lead list, identity graph, or
  marketing segment from customer-verification data;
- Activating an external account-discovery provider solely because an environment value or proxy is present;
- Treating an `exists`, `catchAll`, reason, source, MX, or provider result as consent, lawful basis, marketing
  eligibility, or permission to contact; or
- Retaining processor data under a controller, security, incident, audit, legal-hold, or statutory label without the
  approved role, exact purpose, minimum data, owner, review rule, and evidence.

## End-to-End Flows

### Synchronous Verification

1. An authenticated principal with `verification:run` submits a target address to `POST /verify`, or to the deprecated
   `GET /verify` query. The credit guard debits one organization credit using a random reference.
2. The service lowercases the address, checks the domain prohibition record, and updates the global `emails` row.
3. The verifier first looks up one fixed synthetic address at the same domain in the global SMTP cache. A conclusive hit
   from any organization bypasses DNS, proxy allocation, and SMTP for that address; a miss or nonterminal hit resolves
   MX records, leases a proxy, and sends plaintext SMTP commands. If the domain is not catch-all, the same cache-first
   process runs for the real target address.
4. Catch-all or blacklisted outcomes, including a cached synthetic outcome, can fan out to the four currently selected
   HTTP account-discovery adapters when the HTTP proxy setting exists.
5. The service persists a new `email_verifications` row during the ordinary source-driven flow and returns it. The
   attempted `lastVerificationId` update is dropped by `EmailService`, so `emails` is not linked to the new row; only
   its existence value is updated. No customer organization is stored on either row.

### Asynchronous Verification

1. The API writes the target address, organization ID, and credential ID to an async BullMQ job and returns its job ID.
2. A worker runs the synchronous service. Results represented by `GreylistedException` include the address and retry with custom
   backoff; other errors can also become BullMQ failure text.
3. Polling requires the same organization and returns state alone until completion, then returns the serialized
   verification result without its database creation time. No terminal removal policy is configured.

### CSV Batch Verification

1. The multipart interceptor writes the source object under the authenticated organization prefix before request-file
   and CSV-row validation finish.
2. The batch parent job stores organization/credential ownership plus the object location. Its validation pass reads
   every row, validates the `email` field, and debits the organization once using the parent job ID and row count.
3. Its processing pass reads the object again and creates one organization-scoped async child job per address, linked
   to the parent and tagged with the batch ID.
4. When BullMQ reports that dependencies no longer require waiting, the parent streams every `email_verifications` row
   matching the batch ID into a result CSV and uploads it under the derived result key. Failed dependencies can leave
   the parent waiting rather than produce a completed result.
5. The parent stores the `s3://` result location and finishes. An authenticated same-organization caller can stream the
   result. Neither source nor result objects, parent jobs, child jobs, nor matching PostgreSQL rows are currently
   removed by age.

### Internal Email Cache Administration

The Swagger-hidden `/emails` controller permits a `platform:admin` to create, list, read, and update global raw-address
cache rows. `GET` and `PATCH /emails/:email` put the raw address in the URL, while not-found/conflict errors echo it in
the response text. This is an internal operator surface, not a customer verification endpoint. It does not supply
organization ownership, deletion, rights intake, or approved incident access; plans 03, 04, 07, 13, 20, and 29 must
provide the applicable boundaries.

absolute maximum, warning threshold, manual-hold reasons/owner/review/expiry, and deterministic escalation owner.
Until then, this contract does not invent a value or treat missing cleanup as permission for indefinite retention.

The DNS record cache in EV-11 is not the SMTP probe cache in this table. Its current approximately 1,000-day Redis expiry is
a unit mismatch and must not be described as a 24-hour control.

## Marketing and Suppression Boundary

An email-verification result is only a technical deliverability signal. It does not establish that an address belongs
to a particular person, that the person consented, that a lawful basis exists, that marketing is eligible, or that a
sender has permission to contact the address.

This repository does not compose or send commercial messages. It does not own sender identity, message content,
subject lines, header accuracy, postal-address disclosures, unsubscribe presentation or processing, campaign-specific
suppression, final recipient selection, or other sender obligations. Customer-controller deletion or suppression
instructions for data retained by LeadEmailFinder belong to plans 20 through 22 and 31; they do not replace the customer's own
final suppression system.
